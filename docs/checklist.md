## 입력 (마우스 · 키보드 · 게임패드)

### 마우스 클릭 후 선택 하이라이트 잔존

- 기대 결과: 마우스로 버튼을 누르면 키보드 선택 테두리(Highlighted)가 사라진다.
- 실제 결과: `UI/Click` 액션 콜백에서 `SetSelectedGameObject(null)` 을 호출해도 테두리가 그대로 남는다.
- 원인: 액션 콜백은 입력 갱신 단계에서, `EventSystem` 은 `Update` 에서 돈다. 콜백이 먼저 선택을
  지워도 같은 프레임 뒤쪽에서 `Selectable.OnPointerDown` 이 자기 자신을 다시 선택한다.
  (`InputSystemUIInputModule.ProcessPointerButton` → `ExecuteEvents.ExecuteHierarchy(pointerDownHandler)`)
- 수정 내용: `UIInputRouter` 가 콜백에서는 요청 플래그만 세우고, 실제 해제는 `LateUpdate` 에서
  수행하도록 변경. `LateUpdate` 는 `EventSystem.Update` 보다 뒤이므로 모듈이 되살린 선택을 덮는다.

### 마우스 클릭 직후 게임패드 · 키보드 입력 무반응

- 기대 결과: 마우스로 클릭한 뒤 게임패드 스틱을 기울이면 포커스가 되살아난다.
- 실제 결과: 선택이 `null` 이라 `Navigate` 가 적용될 대상이 없어 아무 일도 일어나지 않는다.
  게임패드에는 포인터가 없어 여기서 조작 수단을 완전히 잃는다.
- 원인: 위 항목의 선택 해제와 짝이 되는 복구 경로가 없었다.
- 수정 내용: `UIInputRouter` 가 `UI/Navigate` · `UI/Submit` 을 구독해, 선택이 비어 있으면
  현재 화면의 첫 버튼(`ScreenFlowController.CurrentFirstSelected`)을 다시 선택한다.
- 다시 확인한 결과:

### 선택 복구 직후 첫 버튼이 저절로 눌림

- 기대 결과: 마우스 클릭 후 Enter(또는 패드 A)를 처음 누르면 포커스만 되살아나고,
  버튼 실행은 그다음 입력부터 일어난다.
- 실제 결과: 포커스가 되살아나는 동시에 그 버튼이 즉시 실행된다. 타이틀에서 Enter 한 번에
  게임이 시작되고, 확인 팝업에서는 팝업이 곧바로 닫힌다.
- 원인: 모듈은 Submit 을 **처리 시점의** `currentSelectedGameObject` 에게 보낸다
  (`InputSystemUIInputModule.ProcessNavigation` 말미). 액션 콜백에서 미리 복구해두면
  같은 프레임에 모듈이 그 버튼을 Submit 대상으로 삼는다.
- 수정 내용: 복구도 `LateUpdate` 로 미뤘다. 그 프레임에는 모듈이 "선택 없음" 으로 처리해
  아무 일도 일어나지 않고, 다음 프레임부터 정상 조작된다. 첫 입력이 복구에 소비되는
  콘솔 UI 의 일반적인 동작과 같다.
- 다시 확인한 결과:

### 스틱을 놓을 때 포커스가 되살아남

- 기대 결과: 게임패드 스틱을 중립으로 되돌리는 동작은 아무 일도 하지 않는다.
- 실제 결과: `UI/Navigate` 가 PassThrough Vector2 라 스틱을 놓을 때도 `performed` 가 발생해

- 원인: 값의 크기를 확인하지 않고 콜백 발생 자체를 신호로 사용했다.
- 수정 내용: `navigateDeadzone`(기본 0.2) 미만의 입력은 무시한다.

### EventSystem 이 프로젝트 액션 에셋이 아니라 패키지 기본 에셋을 보고 있었음

- 기대 결과: 키보드·게임패드 조작이 `Assets/InputSystem_Actions` 의 UI 맵 바인딩대로 동작하고,
  `EventSystem` 과 `UIInputRouter` 가 같은 액션을 공유한다.
- 실제 결과: 겉보기에는 정상 동작한다. 그러나 `InputSystem_Actions` 의 UI 맵을 고쳐도
  포커스 이동·Submit 에는 반영되지 않고 라우터만 반응한다. 입력 표에 적어 둔 바인딩과
  실제로 화면을 움직이는 바인딩이 다른 상태였다.
- 원인: `InputSystemUIInputModule` 을 EventSystem 에 붙이면 Unity 가 `m_ActionsAsset` 에
  패키지 내장 `DefaultInputActions`(guid `ca9f5fa9…`)를 기본값으로 꽂아 둔다. 이 값을 한 번도
  바꾸지 않아 **모듈은 패키지 에셋을, 라우터는 프로젝트 에셋(guid `052faaac…`)을** 보고 있었다.
  두 에셋의 UI 맵 바인딩이 아직 같았고, 프로젝트 에셋은 Project-wide Actions 로 등록돼 있어
  런타임에 자동으로 Enable 된다. 그래서 어느 쪽도 죽지 않아 증상으로 드러나지 않았다.
- 수정 내용: EventSystem 의 `Actions Asset` 에 `InputSystem_Actions` 를 지정했다.
  UI 맵의 액션 이름 10개가 모두 같아 나머지 필드는 Unity 가 이름으로 맞춰 채운다.
  씬에 남은 `DefaultInputActions` 참조가 0 인 것으로 확인했다.

### 진열대에서 상단 PauseButton 으로 이동 불가

- 기대 결과: 키보드 방향키·게임패드로 진열대를 좌우로 훑고, 위로 빠져나가 일시정지 버튼에

- 실제 결과: 진열대 안에서만 맴돌고 `PauseButton` 에 선택이 닿지 않는다. 마우스로는 눌리는데

- 원인: 씬의 Selectable 14개가 전부 Navigation `Automatic` 이었다. Automatic 은 방향과 거리로
  다음 대상을 추정하는데, 진열대 5개가 200px 간격으로 밀집해 있고 `PauseButton` 은 화면
  반대쪽 위에 떨어져 있어 후보로 잡히지 않는다. 선택 계열 입력은 배선된 경로로만 이동한다.

  하나만 건 이유는 도달 가능성만 확보하면 요건이 충족되고, 배선이 늘수록 어긋날 자리도
  늘기 때문이다. 첫 포커스가 맨 왼쪽이므로 Right ×4 → Up 으로 닿는다.

### 영업시간 게이지가 키보드·게임패드 포커스를 가로챔

- 기대 결과: 게이지는 표시 전용이므로 Navigate 대상이 아니어야 한다.
  진열대에서 위로 이동하면 PauseButton 으로 가야 한다.
- 실제 결과: `Progress Slider_Yellow` 프리팹의 `Interactable` 이 켜져 있어 Slider 가

- 수정 내용: `HudController.Awake()` 에서 `timerGauge.interactable = false`.

## 피드백

### 판정 알림 토스트 — 글자가 배경 없이 떠서 읽히지 않음

- 기대 결과: 판정 직후 `성공!` / `실패..` 문구가 0.5초간 뚜렷하게 읽힌다.
- 실제 결과: 문구가 쟁반 아이콘·패널 무늬 위에 그대로 겹쳐 형태가 묻힌다.
  성공 색(초록)과 실패 색(빨강)의 구분도 배경 무늬 때문에 약해진다.
- 원인: 글자에만 색을 주고 배경을 두지 않았다. 대비가 뒤에 무엇이 오는지에 따라 달라지므로
  일정한 가독성을 보장할 수 없다.
- 수정 내용: `ToastMessage` 에 배경 `Image`(`Splash4`) 를 넣고, 배경과 글자를 **같은 색
  계열로 함께** 바꾼다. 켜고 끄는 대상도 텍스트에서 `root`(배경 + 글자)로 옮겼다.
- 이어서 발견한 것: 배경과 글자를 **같은 색으로 두면 글자가 배경에 묻혀 사라진다.**
  배경(`successColor` / `failColor`)은 연한 색, 글자(`successTextColor` / `failTextColor`)는
  같은 계열의 진한 색으로 두 값을 인스펙터에 따로 노출해 밝기 차를 확보했다.
  `Image.color` 가 스프라이트에 곱해지므로 배경 색을 어둡게 넣으면 얼룩 테두리까지 뭉개진다.

### 어느 버튼에 포커스가 있는지 구별되지 않음

- 기대 결과: 키보드·게임패드로 이동할 때 지금 선택된 버튼이 한눈에 보인다.
- 실제 결과: 선택된 버튼이 거의 표시되지 않는다. 마우스 hover 와 키보드 포커스도
  구별되지 않아, 방향키를 눌러도 선택이 움직이고 있는지 알 수 없다.
- 원인: 버튼 14개가 Unity 기본 ColorBlock 값을 그대로 쓰고 있었다.
  `m_SelectedColor` 가 `0.9607`(흰색 대비 4% 어두움)이라 알록달록한 케이크 스프라이트
  위에서는 차이가 묻힌다. 게다가 `m_HighlightedColor` 와 값이 **완전히 같아** 두 상태를
  색으로 구분하는 것 자체가 불가능했다.
- 수정 내용: 색을 더 진하게 바꾸는 대신 `FocusRing` 을 만들었다. 선택된 버튼을 따라다니며
  네 변의 테두리를 두르는 오브젝트 하나로, `UIRoot` 아래 `Screen_Fade` 바로 앞에 둔다
  (화면 4개 위에는 그려지고 페이드에는 덮이는 순서).
  - 버튼마다 테두리를 붙이지 않은 이유: Selectable 이 14개라 하나만 빠뜨려도 그 버튼에서만
    조용히 표시가 사라진다. 선택은 언제나 하나뿐이므로 테두리도 하나면 된다.
  - 테두리용 스프라이트를 만들지 않았다. 스프라이트 없는 `Image` 는 단색 사각형이므로
    네 변을 Stretch 앵커로 붙여 두면 링 크기만 바꿔도 알아서 따라온다.
  - 잠긴 버튼(판정 중 진열대)에는 두르지 않는다. 누를 수 있는 것처럼 보이면 안 된다.
- 이어서 발견한 것: 선택이 비었을 때 숨기는 것만으로는 부족했다. 화면이 바뀔 때
  `ScreenFlowController` 가 첫 버튼을 선택하므로, **마우스로 화면을 넘기면 곧바로 테두리가
  뜬다.** 포인터 조작 중에는 선택이 지워지는 것을 기대했지만, 클릭으로 화면이 바뀐 경우
  `ClearSelection` 이 `screenFlow.Top != topAtPointerPress` 로 일찍 빠져나가 지우지 않는다.
  - 수정: "선택이 있는가" 와 "지금 키보드·패드로 조작 중인가" 를 분리했다.
    `UIInputRouter.IsSelectionMode` 를 두어 Navigate·Submit 에 켜고 포인터 클릭에 끈다.
    `FocusRing` 은 이 값이 true 일 때만 테두리를 두른다.
  - Submit 도 켜는 쪽에 넣었다. 마우스로 누른 뒤 Enter 를 치면 `RestoreSelection` 이 첫
    버튼을 되살리는데, 이때 테두리가 숨어 있으면 포커스가 보이지 않는 곳으로 옮겨간 뒤
    다음 Enter 에 그 버튼이 실행된다. 무엇이 눌릴지 모르는 상태가 되므로 제외할 수 없다.

## 화면 전환

### 영업시간 종료 시 결과 화면으로 즉시 전환됨

- 기대 결과: 영업이 끝났다는 사실을 인지하고, 마지막 판정 결과를 확인한 뒤 결과 화면으로
  넘어간다.
- 실제 결과: 남은 시간이 0 이 되는 프레임에 바로 `ShowResult()` 가 불려 화면이 즉시 바뀐다.
  마지막에 담은 것이 성공이었는지 실패였는지 볼 수 없고, 게임이 끝난 것인지 오작동인지도
  구분되지 않는다. 특히 종료 직전 판정의 토스트(0.5초)가 뜨는 도중에 화면이 사라진다.
- 원인: `GamePlayController.OnGameOver` → `PlayState.HandleGameOver()` → `ShowResult()` 가
  한 프레임 안에 이어졌다. 시작에는 카운트다운이 있는데 종료에는 대응되는 연출이 없었다.
- 수정 내용: `CountdownView` 에 `PlayTimeout()` 을 추가해 `Timeout!!` 을 1초 표시한 뒤
  `ShowResult()` 를 호출하도록 바꿨다. 시작 카운트다운과 **같은 패널(`CountPanel`)** 을
  재사용해 위치·크기·폰트를 두 번 맞추지 않는다. 화면 전환 자체의 페이드는 기존
  `ScreenFade` 가 그대로 맡는다.
  - `PlayTimeout()` 은 끝난 뒤 패널을 끄지 않는다. 끄면 페이드가 시작되기 전 한 프레임 동안
    플레이 화면이 드러난다.
  - 연출 중 조작 차단은 시작 카운트다운과 같은 처리로 묶었다(`PlayState.isPlayingSequence`).
    플래그를 두 개 두면 한쪽만 검사하는 실수가 난다.
- 다시 확인한 결과:
