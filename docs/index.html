0.8초 뒤에 깨어난 코루틴이 새 판의 손님을 넘겨 버린다

판정 직후 곧바로 다음 손님으로 넘기면 무엇을 잘못 눌렀는지 볼 시간이 없다. 그래서 0.8초 지연 + 진열대 잠금을 넣었는데, 이 대기가 화면 수명보다 오래 살아남는 것이 문제였다.

증상
결과 화면에서 다시하기를 0.8초 안에 누르면, 새 판이 시작되자마자 손님이 한 명 그냥 넘어간다.
원인
await는 화면이 바뀌어도 대기를 취소하지 않는다. 이전 판의 대기가 뒤늦게 깨어나 새 판의 NextCustomer()를 호출한다.
판단
CancellationTokenSource를 하나 더 두는 대신 정수 세대 토큰을 골랐다. 취소는 대기를 끊을 뿐 "이 대기가 어느 판의 것인가"를 알려주지 않는다. 토큰을 비교하면 깨어난 쪽이 스스로 자기가 구세대임을 알고 조용히 빠진다.

Input System 콜백과 EventSystem이 같은 프레임에서 서로를 덮어쓴다

마우스로 누르면 키보드 선택 테두리를 지우고, 방향키를 넣으면 되살린다. 개념은 두 줄인데 콜백에서 곧바로 실행하면 둘 다 실패한다. 액션 콜백은 입력 갱신 단계에서, EventSystem은 Update에서 돌기 때문이다.

증상 A
콜백에서 SetSelectedGameObject(null)을 불러도 테두리가 그대로 남는다.
증상 B
마우스로 클릭한 뒤 Enter를 한 번 치면 포커스가 복구되는 동시에 그 버튼이 즉시 실행된다. 타이틀에서 Enter 한 번에 게임이 시작되고, 확인 팝업은 열리자마자 닫힌다.
원인
A는 콜백이 지운 선택을 같은 프레임 뒤쪽의 Selectable.OnPointerDown이 되살린다. B는 모듈이 Submit을 처리 시점의 currentSelectedGameObject에게 보내기 때문이다.
판단
둘 다 한 프레임 뒤로 미루는 것으로 해결된다. 콜백은 요청 플래그만 세우고 실제 반영은 LateUpdate가 한다. 그 프레임 입력 하나를 잃지만, 첫 입력이 포커스 복구에 소비되는 것은 콘솔 UI의 일반적인 동작이라 그대로 뒀다.
Screens/ScreenFlowController.cs · UIStateBase.cs 스택 상태 머신 · 잠금 경로 분리

일시정지 중에 위 방향키가 아래 화면의 버튼을 누른다

화면 전환은 Stack<UIStateBase> 하나로 처리한다. SetScreen은 스택을 비우고 새로 쌓고, Push/Pop은 위에 겹친다. 결과 화면이 최종 점수를 읽어야 해서 아래 화면을 끄지 않는 것이 의도였는데, 그 때문에 아래 버튼이 살아 있었다.

증상
일시정지 중 위 방향키 → 선택이 Screen_Play/TopNav/PauseButton으로 넘어가고 Enter로 실제 눌린다. 일시정지가 스택에 한 겹 더 쌓여 계속하기를 두 번 눌러야 빠져나온다.
원인
전체 화면 Image의 Raycast Target은 포인터만 막는다. Navigate는 레이캐스트를 쓰지 않고 Selectable.FindSelectable이 캔버스 전체를 훑으므로 패널 경계라는 개념이 없다.
판단
버튼의 interactable을 직접 만지지 않고 CanvasGroup을 썼다. 진열대 버튼은 ShelfView가 판정 잠금으로 껐다 켜는데, 여기서 값을 직접 되돌리면 판정 중이던 잠금이 풀린다. CanvasGroup은 별개의 관문이라 두 조건이 모두 참일 때만 눌린다.
Screens/FocusRing.cs 플래그 겸용이 만든 버그

화면을 넘겼는데 테두리가 이전 화면의 자리에 남는다

Unity 기본 ColorBlock은 Selected와 Highlighted 색이 완전히 같아 두 상태를 색으로 구분하는 것 자체가 불가능했다. 버튼 14개에 색을 하나씩 다시 넣는 대신, 선택된 하나를 따라다니는 테두리 오브젝트를 하나만 만들었다. 선택은 언제나 하나뿐이므로 테두리도 하나면 된다.

증상
타이틀에서 키보드로 시작을 누르면, 카운트다운이 끝난 뒤 테두리가 화면 중앙에 나타난다. MenuButton_Start의 자리가 그대로 남은 것이다.
원인
매 프레임 돌던 Fit()을 "선택이 바뀔 때만"으로 줄이면서 lastSelected를 선택 추적과 맞춤 완료 표시 두 용도로 겸용했다. 새 버튼으로 바뀌며 표시를 소비했는데, 그 버튼이 카운트다운 중이라 IsInteractable()이 거짓이어서 Fit() 전에 빠져나갔다.
판단
needsFit을 lastSelected와 분리해, 실제로 Fit()을 실행한 뒤에만 내린다. 화면 전환마다 초기화를 심는 방법도 검토했지만, 증상이 드러나는 시점이 전환이 아니라 카운트다운 종료라 같은 문제가 남고, 전환 경로 세 곳 중 하나만 빠뜨려도 조용히 재발한다.

최적화

매 프레임 도는 코드에서 뺄 수 있는 것

타이머는 매 프레임 갱신되지만, 그 값을 받는 쪽이 전부 매 프레임 일할 필요는 없다. 아래 네 건은 "언제 갱신을 건너뛸 수 있는가"를 기준으로 정리한 것이다.

초 단위가 바뀔 때만 문자열을 만든다

TimerText를 매 프레임 갱신하면 초당 60번 int.ToString()이 새 문자열을 할당한다. 표시되는 값은 초당 1번만 바뀌므로 lastDisplayedSecond와 비교해 같으면 즉시 반환한다.

할당 60/s → 1/s

경고 색은 상태가 바뀐 순간에만

게이지 점멸은 매 프레임 Lerp가 필요하지만 글자 색은 켜짐/꺼짐 두 값뿐이다. lastDangerState로 경계를 넘는 프레임에만 timerText.color를 쓴다. TMP는 색 대입마다 메시를 다시 올린다.

메시 갱신 60/s → 경계 1회

점멸 위상을 남은 시간으로 잡는다

Mathf.PingPong(remainingTime * pulseSpeed, 1f). Time.time을 쓰면 일시정지 중에도 점멸이 계속 돌아 시간이 흐르는 것처럼 보인다. 남은 시간을 위상으로 쓰면 시계가 멈출 때 점멸도 함께 멈춘다.
